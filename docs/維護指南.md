# 維護指南（給接手的人）

這份是寫給**沒有工程背景**的接手者看的。假設你會用電腦、但沒寫過程式，
需要靠 AI 工具（Claude Code、ChatGPT 之類）輔助來維護這個系統。

如果你有技術背景，這份還是值得掃一遍——「不能亂改的地方」那節記錄了幾個
外表看起來像 bug、其實不能動的東西。

---

## 第一件事：先弄清楚你手上有什麼

在動任何東西之前，先確認你能登入這四個地方。少任何一個，維護工作都會做不完整。

| 服務 | 你要能做什麼 | 怎麼確認 |
|---|---|---|
| **GitHub** | 看得到 `iDA-Workplace/leave-system-app`，而且能改檔案 | 打開 repo，隨便點一個檔案，右上角有沒有鉛筆（編輯）圖示 |
| **Vercel** | 看得到 `leave-system-app` 專案的部署紀錄 | 進 Deployments 頁面，看得到一列一列的部署紀錄 |
| **Supabase** | 進得去資料庫，看得到真實資料 | Table Editor 開 `leave_requests`，確認有資料、筆數不是 0 |
| **Slack App** | 能修改 App 設定 | <https://api.slack.com/apps> 看得到這個 App |

**進不去的話先去要權限，不要硬著頭皮開始改東西。**
帳號歸屬與交接流程見「系統交接與資料保全」文件。

## 第二件事：搞懂「改一個東西」會發生什麼

這是最重要的觀念，弄懂這個，很多事情就不會慌。

系統分成三層，**改不同的層，做法完全不一樣**：

### 第 1 層：畫面與功能（改程式碼）

想改的是「按鈕文字」「欄位順序」「多一個選項」「顏色」這類的。

做法：改 GitHub 上的程式碼 → Vercel 自動重新部署 → 1~2 分鐘後上線。

**大家不需要重新安裝 App**，下次打開就是新版本了。

### 第 2 層：資料庫結構（跑 SQL）

想改的是「多一個欄位」「改權限規則」這類的。

做法：寫一份 SQL 檔案放進 `supabase/migrations/` → **到 Supabase 後台手動執行它**。

⚠️ **這一層不會自動執行**。放進資料夾只是留紀錄，一定要自己去 Supabase 的
SQL Editor 貼上去跑一次。忘了跑的話，網站會因為找不到欄位而出錯。

### 第 3 層：Slack 通知（改 Edge Functions）

想改的是「通知文字」「發送時間」這類的。

做法比較特別，見下方「Slack 通知怎麼改」那一節，有幾個很容易踩的坑。

## 出事了怎麼查

### 網站打不開／畫面一片空白

1. 開網站，按 **F12** 叫出開發者工具，切到 **Console** 分頁
2. 重新整理頁面
3. 看有沒有紅色的錯誤訊息

常見錯誤與原因：

| 錯誤訊息長這樣 | 通常是什麼問題 |
|---|---|
| `Invalid supabaseUrl` | Vercel 的環境變數 `VITE_SUPABASE_URL` 沒填、填錯、或改了之後沒重新部署 |
| 畫面空白但沒有錯誤 | 去 Vercel 的 Deployments 看最新那筆是不是紅色 Error |

4. 同時去 **Vercel → Deployments**，確認最新一筆是綠色 `Ready` 還是紅色 `Error`
5. 如果是紅色，點進去看 Build Logs，錯誤原因會寫在裡面

**回到上一個能用的版本**：Vercel 的 Deployments 列表裡，找一筆之前綠色正常的，
點右邊的 `⋯` → **Promote to Production**。這會立刻把網站切回那個版本，
是出事時最快的止血方法。

### Slack 沒發通知

依序確認：

1. **Slack App 還在那個頻道裡嗎**——App 被踢出頻道是最常見的原因。
   在頻道輸入 `/invite @App名稱` 重新邀請。
2. **排程還在嗎**——到 Supabase → SQL Editor 跑：
   ```sql
   select jobname, schedule from cron.job;
   ```
   應該要看到 `daily-leave-digest`（早上 9 點）跟 `daily-leave-preview`（下午 4 點）。
3. **手動觸發試試看**——Supabase → Edge Functions → 進到該支 function →
   Overview → 右上角 **Test**。詳細做法見
   [`supabase/functions/README.md`](../supabase/functions/README.md) 的「六、測試」。
4. **看錯誤紀錄**——該支 function 的 **Logs** 分頁。

### 有人說「我看不到我的假單」或「按了核准沒反應」

這類「操作有回應但資料沒變」的問題，**十之八九是資料庫權限規則（RLS）的問題**。

Postgres 的 RLS 有一個很坑的特性：**當規則把所有目標資料列都排除掉時，
它會回報「成功、影響 0 筆」，而不是報錯**。所以畫面上會顯示成功的提示，
但資料其實完全沒有改到。

這個專案的歷史上已經因為這個原因修過好幾次（見
[`supabase/migrations/README.md`](../supabase/migrations/README.md) 裡
`20260811`、`20260812`、`20260813` 那幾筆）。遇到這種症狀，
先往 RLS 政策的方向查，不要一直看前端程式碼。

## 不能亂改的地方

這幾個東西外表看起來很怪、甚至像是寫錯了，**但都不能動**。

### 1. Slack function 的網址叫 `clever-responder`

排程實際呼叫的網址是：

```
https://<專案代號>.supabase.co/functions/v1/clever-responder
```

`clever-responder` 是 Supabase 網頁編輯器建立 function 時給的**隨機預設名字**，
當初部署時忘了改。名字雖然莫名其妙，但**它就是每日請假公告那支程式**，
改掉名字排程就會找不到它。

要改的話，必須同時更新資料庫裡兩條排程的網址，不能只改一邊。
沒有非改不可的理由就別動。

### 2. 兩條排程的差別只在網址結尾

- 早上 9 點：`.../clever-responder`（發「今天誰請假」）
- 下午 4 點：`.../clever-responder?scope=next`（發「下個上班日誰請假」）

**結尾那個 `?scope=next` 就是全部的差別。** 少了它，下午那則會變成
跟早上一模一樣的內容（這個 bug 實際發生過）。

### 3. `standalone.ts` 要跟 `index.ts` 一起改

`supabase/functions/` 底下有三支 function 各有兩份程式碼：

- `index.ts` — 真正的原始碼，用指令列部署時用這份
- `standalone.ts` — 把共用程式碼合併進單一檔案的版本，**用網頁編輯器部署時只能用這份**

兩份的邏輯必須一樣。**改了 `index.ts` 一定要同步改 `standalone.ts`**，
不然你在網頁後台部署的會是舊版本，會出現「我明明改了但沒生效」的鬼打牆。

（`slack-interactions` 例外，它本來就只有一份檔案。）

### 4. Supabase 專案代號被寫死在很多地方

專案代號 `dwwswsqwgioneedpsbsu` 出現在：
Vercel 的環境變數、資料庫裡兩條排程的網址、Slack App 的設定、
以及每個人瀏覽器裡儲存的登入狀態。

**絕對不要用「匯出資料再建一個新的 Supabase 專案」的方式搬家**——新專案會拿到
不同的代號，上面四個地方全部要改，而且**所有人的登入帳號要重建、密碼全部重設**。
要搬家請用 Supabase 內建的「轉移專案」功能，代號才會跟著保留。

### 5. `.env` 檔案目前有被 git 追蹤

這個檔案裡有 Supabase 的網址與公開金鑰。它照理說不該進版控，
但目前是進去的。**這兩個值本來就是設計成公開給瀏覽器用的**
（安全性靠資料庫的 RLS 規則把關），所以不是立即的資安問題，
但屬於待整理項目。

要處理的話順序很重要：**先確認 Vercel 上的環境變數是對的，再把 `.env` 移出版控**，
反過來做會讓網站建置失敗。

## 特休怎麼算（碰之前務必讀完這節）

特休是整個系統**最容易改錯、而且改錯最不容易被發現**的地方。
它牽涉三個彼此相依的位置，只改一邊就上線會出事。

### 公司的制度（2026-09 向人資確認）

**「該年度跨進哪個級距，就給那個級距的全額天數，不打折。」**

以 2025/4/28 到職的同仁為例：

| 年度 | 天數 | 什麼時候給 |
|---|---|---|
| 2025（到職當年） | 3 天 | 滿 6 個月、也就是 2025/10/28 之後才給 |
| 2026 | 7 天 | **1/1 就給滿**，不必等到 4/28 滿一年 |

也就是說「滿 6 個月才給」這道門檻**只存在於到職當年**，第二年起都是年初就全額給予。
員工當年度離職時，人資會另外依勞動部的年假系統按比例結算 —— 那是人資手動處理的，
系統不負責。

實作上就是：看 **12/31 當天的年資**落在勞基法第 38 條的哪個級距，給該級距的全額。
12/31 的年資正好是這個人在該年度內達到的最高級距。

### 三個必須一起改的地方

| 位置 | 負責什麼 | 改了要做什麼才會生效 |
|---|---|---|
| `supabase/migrations/20260911_annual_leave_year_end_bracket.sql` | 天數怎麼算（資料庫的 `annual_leave_summary`） | **手動去 Supabase SQL Editor 跑** |
| `src/lib/leaveEntitlements.js` 的 `isAnnualLeaveType` | 前端怎麼認出「這是特休」 | 合併到 `main`，Vercel 自動部署 |
| `supabase/functions/slack-interactions/index.ts` | Slack 查餘額、送假單時的額度檢查 | **手動貼到 Supabase 後台重新部署** |

**三邊的生效方式都不一樣**，這是最容易漏的地方——改了程式碼推上去，
以為就好了，結果資料庫和 Slack 還是舊的。

### 怎麼辨識「特休」這個假別：看旗標，不要看名字

`leave_types` 有一個 `is_annual` 欄位，上面三個地方都是靠它判斷的。

**以前是比對名稱**（`name = '特休假'` 或 `name.includes('特休')`），結果只要有人到
「假別名稱設定」把它改名，四個地方會同時失效**而且不會報錯**：已使用天數變 0、
額度改吃一般假別的固定值、Slack 算錯。假單都還在，只是統計抓不到。

所以：**假別可以自由改名，但絕對不要改回用名字判斷。**

如果哪天真的要新增第二種「依年資計算」的假別，把那一列的 `is_annual` 設成 `true` 即可，
不用改程式碼。確認目前標了哪些：

```sql
select id, name, is_annual from leave_types order by name;
```

### 已使用天數包含「審核中」

計算「今年請掉幾天特休」時，**已核准和審核中的都算**。

這是刻意的：如果只算已核准的，同一個人可以連送好幾張假單，每一張送出當下檢查都會過
（前面幾張還在審核中、不列入計算），等主管一次全部核准就直接超額。
被駁回或收回的假單狀態不是 pending，時數會自動回到可用額度。

其他假別在 `fetchUsedHours` 裡本來就是這樣算的，兩邊規則一致。

### 每年 1/1 是分界點，第一次跨年要實際檢查

年度一換，所有人的額度重新計算、已使用天數歸零。**建議每年 1 月初挑一天實際登入，
抽查幾位同仁的天數對不對**，特別是前一年剛跨過級距的人（滿 1 年、滿 3 年、滿 5 年、
滿 10 年的那幾位）。

### 改動之前一定要先驗算

這是法定權益，算錯會直接影響同仁。改完先跑這段對照，確認沒有人的天數變少：

```sql
select full_name as 姓名, hire_date as 到職日,
       entitled_days as 特休天數, used_days as 已使用
from annual_leave_summary
order by hire_date;
```

如果不確定某個年資該給幾天，用勞動部的
[特別休假日數試算系統](https://calcr2.mol.gov.tw/RestDays) 對一次答案。

## Slack 通知怎麼改

完整說明在 [`supabase/functions/README.md`](../supabase/functions/README.md)，
這裡只講最容易踩的三個坑：

1. **改完 `index.ts` 要同步改 `standalone.ts`**（見上一節）
2. **在網頁編輯器新建 function 時，名稱欄位要先改掉再按 Deploy**——
   忘了改的話網址就定死成隨機名字，之後改不動（`clever-responder` 就是這樣來的）
3. **部署後要確認回傳格式**——網頁編輯器有時會帶一份範例模板，
   如果貼程式碼時沒刪乾淨，測試會回傳範例的訊息而不是報錯，
   很容易誤以為成功了

## 定期該做的事

| 頻率 | 做什麼 |
|---|---|
| **每季** | 把資料庫匯出成 CSV 備份，存到公司雲端硬碟（做法見下方） |
| **每季** | 打開最近一次的備份檔，實際確認資料齊不齊——**沒驗證過的備份等於沒備份** |
| **動大手術之前** | 清測試資料、轉移帳號、改資料結構之前，一定先完整備份一次 |
| **有人離職時** | 檢查他的帳號是否還留在 GitHub org / Vercel / Supabase，該移除的移除 |

### 怎麼正確匯出備份（有個編碼的坑）

1. Supabase → **SQL Editor**，貼上下面這段查詢後執行

   這段查詢會把資料庫裡的代碼**翻譯成人看得懂的名字**（直接用 `select *`
   匯出的話，申請人欄位會是一串看不懂的英數字代碼）：

   ```sql
   select
     lr.id,
     requester.full_name as 申請人,
     requester.department as 部門,
     proxy.full_name as 代理人,
     lt.name as 假別,
     lr.start_date as 開始日,
     lr.end_date as 結束日,
     lr.start_time,
     lr.end_time,
     lr.hours as 時數,
     lr.reason as 事由,
     lr.status as 狀態,
     lr.created_at as 建立時間
   from leave_requests lr
   left join users requester on requester.id = lr.requester_id
   left join users proxy on proxy.id = lr.proxy_user_id
   left join leave_types lt on lt.id = lr.leave_type_id
   order by lr.created_at desc;
   ```

2. 點結果下方的 **Download CSV**

3. ⚠️ **不要用滑鼠雙擊打開這個 CSV 檔**

   檔案本身是 UTF-8 編碼，但 Windows 的 Excel 雙擊開啟時會用錯誤的編碼解讀，
   中文會變成亂碼。**更糟的是，如果這時候按了儲存，中文就會被永久破壞、救不回來。**

   正確的開啟方式二選一：
   - **Google 試算表**：檔案 → 匯入 → 上傳（編碼會自動判斷正確）
   - **Excel**：資料 → 取得資料 → 從文字/CSV → 把「檔案原始格式」手動選成
     **65001: Unicode (UTF-8)**

4. 除了 `leave_requests`，這幾張表也要定期備份：
   `leave_approvals`（簽核紀錄）、`users`（員工基本資料）、
   `annual_review_participants`、`review_responses`、`review_evaluations`（考核）

## 用 AI 工具維護這個系統

如果你不會寫程式，這是最實際的做法。這個專案對 AI 工具特別友善，
因為**程式碼註解全部是中文，而且寫的是「為什麼這樣做」而不只是「做了什麼」**。

### 建議的做法

1. 用 AI 的程式輔助工具（例如 Claude Code），把整個 repo 給它看
2. **先叫它讀相關的檔案再動手**，不要一開口就叫它改
3. 描述你要的**結果**（「我要在請假表單多一個欄位，讓大家填代理人的分機」），
   而不是描述**做法**（「你去改 LeaveForm.jsx 第 120 行」）——你不需要知道要改哪裡
4. 改完之後，**一定要自己實際打開網站點一遍**確認沒壞，不要只信 AI 說「完成了」

### 給 AI 的開場白，可以這樣寫

> 這是一個公司內部的請假系統，React + Vite + Supabase。
> 請先讀 README.md 和 docs/維護指南.md 了解架構，
> 特別注意「不能亂改的地方」那一節。
> 我想做的是：（描述你要的結果）
> 動手之前請先告訴我你打算改哪些檔案、為什麼。

### 幾個提醒

- **AI 不會知道你資料庫裡的實際狀態**（有哪些員工、目前的權限設定），
  它只看得到程式碼。牽涉資料庫的問題，要自己去 Supabase 查了再告訴它。
- **AI 有時候會自信地講錯**。牽涉到「要付錢」「要刪東西」「要改權限」的操作，
  先停下來查證，不要照做。
- **Claude Code 這類工具不在部署鏈上**。它只是幫你寫程式碼跟推上 GitHub，
  推上去之後就是 Vercel 自動部署，跟 AI 工具無關。所以**你不需要繼承前一個人的
  AI 帳號**，自己申請一個就好。

## 還沒做完的事（交給你了）

這幾件是已知但還沒處理的，接手時可以評估要不要做：

- **`auto-deactivate-delegates` 這條排程可能是殘留的**——名稱看起來屬於已經整個
  刪掉的「代理審核」功能。還沒有確認過，處理前先查清楚它到底在做什麼。
- **`.env` 移出版控**（見「不能亂改的地方」第 5 點的順序提醒）
- **`supabase/migrations/README.md` 是英文的**，可考慮翻成中文
- **Slack App 目前只有一個人能改設定**，建議加第二位協作者
